# R2 golden vectors — the four HELD-CORE steps (for the chip side)

Generated by `python3 -m tools.host_gui.r2_vectors`; the bytes below are copied
out of the shipped `reviews/2026-09-25/r2-hex/manifest.json`, not re-typed.

> **chip_confirmed = false for all four.** They are the R2 readback exercised
> while the core is **held at a breakpoint**, and the chip has not run them:
> `tb_pe_ctrl_r2` instantiates `pe_ctrl` with no core, and `pe_ctrl`'s
> `bp_en`/`bp_hit`/`dbg_hold_r` are internal (only `fv_bp_en`/`fv_bp_hit`/
> `fv_dbg_hold`/`fv_dbg_state` are output taps), so that TB cannot reach
> states 2/3 at all. The expectations are read off the frozen contract
> (`pe_ctrl.v`'s `dbg_state` wire, its `OP_STATUS`/`OP_DUMPCOR` builders and
> the `if (run)` gate on DUMP_CORE) — a **gate the chip must pass**, not
> evidence. The 18 pre-existing steps are unchanged and still 18/18.

## Why these four exist

The chip review's MEDIUM 3: "R2's chip-confirmed STATUS/DUMP_CORE now report
state 2/3, a compatibility surface the R2 vectors never exercise". A chip that
was right on the boot stop and the free-running core, and wrong on the two
debug-hold states, passed 18/18. The chip closed its side of this (M3, the
`state=3 / run=1 / pc=2` case); this is the **golden-package** half that was
still missing.

STATUS payload order is R2's: `status, state, run, target, pc, a, x, y, timer,
faults, words_written`. So step 19 reads **state=2, run=0, pc=1** and step 21
reads **state=3, run=1, pc=2**.

## The pre-state each step assumes

Both are **reachable** core states, and both are the pc/a a real core has after
executing the program the package already ships (`imem` 0x0041 `LDI A,0x41`,
0x1001 `OUT`, 0x4002 `JMP 2`) — an unreachable pre-state proves nothing, which
was the R3 review's MEDIUM 2.

| field | step 19-20 (`v09-status_while_step_paused`) | step 21-22 (`v10-status_while_bp_hit`) |
| --- | --- | --- |
| how a core gets there | one `DEBUG_STEP` from the boot stop: `imem[0]` retires, the core pauses at 1 | free-running with the strap high, stopped ON the armed breakpoint at 2 (stop-before: the instruction at 2 has **not** run) |
| `pc` / `a` | `1` / `0x41` | `2` / `0x41` |
| `x` / `y` / `timer` / `insn` | `0` / `0` / `0` / `0` | `0` / `0` / `0` / `0` |
| run strap (`run`) | `0` | **`1`** — the hit holds the core, it does not drop the strap |
| `faults` / `words_written` | `0` / `3` (the TB's opening 3-word LOAD) | `0` / `3` |
| `bp_addr` / `bp_en` / `bp_hit` / `debug_hold` | `2` / armed / not hit / **held** | `2` / armed / **hit** / **held** |

`x`, `y`, `timer` and `insn` are a preloaded snapshot, not a claim: the shipped
steps never report the `insn` word, so they do not depend on the fetch-mode
question (`imem[pc]` vs the latched register) that the R3 package pins as a
TB-model boundary. `words_written=3` is the existing precondition — replay the
session's opening LOAD as a real framed frame, as the TB already does.

## What each step is actually pinning

* **state encoding** — `dbg_state = dbg_hold_r ? (bp_hit ? 3 : 2) : (run ? 1 : 0)`.
  Only a hold can produce 2/3, and the latched hit is the only thing that
  separates 2 from 3. A chip that swapped them, or that derived the state from
  the strap, answers the boot stop correctly and fails here.
* **run is the strap, not the state** — step 21 is the one that catches it.
  `OP_STATUS` reports `run` from the raw strap, so a live hit arrives as
  `state=3, run=1`; a host that read `run==0` as "stopped" would be told the
  core is stopped and then find `DUMP_CORE` refusing.
* **`DUMP_CORE` is gated on the strap, not the hold** — step 22. `pe_ctrl`:
  `OP_DUMPCOR: if (run) -> ST_NOTREADY`. With the strap still high the core is
  stopped *and* DUMP_CORE refuses, which is the asymmetry a debugger has to
  code around (use `STATUS`, not `DUMP_CORE`, to read a core parked on a
  breakpoint). A chip that gated it on the hold would answer the full header
  here and pass all 18 existing steps. Step 20 is the other half: with the
  strap low, a hold does **not** close the data path, and the DUMP_CORE header
  equals the STATUS header — R2's original `dump_core_header` obligation, restated
  under a hold.
* **a refusal is not a fault** — all four steps assert `faults` unchanged
  (`model_faults=0`), and step 22's response is the bare 1-word `NOT_READY`.

## What the chip has to do to confirm them

1. Copy the four steps' 8 new `.hex` files from `reviews/2026-09-25/r2-hex/`
   into `tb/r2-vectors/`, and re-generate the step table
   (`tb/r2-vectors/r2_steps.txt`, and `R2_CONFORMANCE_RUN.vh`) from the new
   `manifest.json` — the table is derived, so do not hand-edit it. The four
   lines are:

   ```text
   status_reports_the_hold status_while_step_paused.status_reports_the_hold.req.hex status_while_step_paused.status_reports_the_hold.rsp.hex 10 32 0
   dump_core_answers_the_same_header status_while_step_paused.dump_core_answers_the_same_header.req.hex status_while_step_paused.dump_core_answers_the_same_header.rsp.hex 10 32 0
   status_reports_the_hit status_while_bp_hit.status_reports_the_hit.req.hex status_while_bp_hit.status_reports_the_hit.rsp.hex 10 32 0
   dump_core_refused_the_strap_is_high status_while_bp_hit.dump_core_refused_the_strap_is_high.req.hex status_while_bp_hit.dump_core_refused_the_strap_is_high.rsp.hex 10 12 0
   ```

   `R2_NUM_STEPS` goes 18 → 22. The 18 existing lines and their bytes do not
   change, and this repo pins them: a byte fingerprint of all 18 lives in
   `tools/host_gui/tests/test_r2_vectors.py`.
2. Establish the held pre-state. The clean route is the one R3's conformance
   already uses — reach it through the **debug opcodes** on a real core
   (`BP_SET(2)`, then `DEBUG_STEP` from the boot stop for step 19-20; arm and
   run into the breakpoint for step 21-22). If `tb_pe_ctrl_r2` keeps its
   coreless shape, the state has to be forced hierarchically
   (`dut.bp_en`, `dut.bp_hit`, `dut.dbg_hold_r`) as the chip's own M3 case did
   — record that it is forced, because a forced pre-state is the MEDIUM-2
   review item, and note that both of these particular states are ones the R3
   conformance run already demonstrates a real core reaches.
3. Re-run and **report any divergence rather than re-deriving the bytes**: the
   vectors are the acceptance spec, exactly as for the other 18. On a green
   run, flip the four steps to `chip_confirmed: true` with the citation in
   `r2_vectors.CHIP_EVIDENCE` — and the notice and the counts follow from the
   flags, so `test_r2_vectors` will tell you if the prose was left behind.

`status_reports_the_hold` and `status_reports_the_hit` send the **same request
bytes** (`a55a1110000100008afe`) and differ only in what the chip is doing
when it answers — which is the point: the frame carries no debug state, so
every difference between the two responses is chip behaviour.

## Provenance

Expectations derived from the frozen contract semantics, checked against the
chip RTL read-only (`pe_ctrl.v`: the `dbg_state` wire, the `OP_STATUS` /
`OP_DUMPCOR` builders, the `if (run)` DUMP_CORE gate, the `bp_flags` mapping).
No chip file was modified. Host-side evidence: `python3 -m tools.host_gui.r2_vectors --check`
exit 0, and `tools/host_gui/tests/test_r2_vectors.py` (44 tests, including a
byte fingerprint of the 18 confirmed steps and a guard that this notice matches
the flag arithmetic — the R3 review's F1, applied to R2).
