# .known-stale-renders.txt — the PINNED BASELINE for check_diagram_renders.sh
#
# WHY THIS FILE EXISTS, and why it is the same shape as
# wiki/.known-rule-violations.txt rather than something new. That file already
# solved this exact problem for wiki pages: a gate written today meets a corpus
# carrying known defects owned by other people, and the choice is not "green" or
# "red". It is "enumerate them with a reason, or get the gate switched off". A red
# gate nobody can act on is eventually muted, and a muted gate protects nothing —
# so the defects get enumerated here instead, where they are visible, dated, and
# attached to whoever can clear them.
#
# THE SHAPE, and the half that matters. Each line is a render file that is
# KNOWN to differ from a fresh render of its own source, plus a reason:
#     <render-file> <reason...>
# Fields: the first is machine-read, the rest never parsed. A malformed line is a
# HARNESS ERROR, not a skip — a pin this checker cannot read is a pin that has
# silently stopped being enforced, which is the exact failure the anti-staleness
# direction below exists to prevent.
#
# ENFORCED BOTH WAYS, exactly as the page baseline is:
#     a stale render NOT listed here          -> NEW         -> red
#     a listed render that is NO LONGER stale -> STALE-PIN   -> red
# The second direction is the one that makes a pin safe to write. Without it the
# pin outlives its defect: the owner re-renders, the entry stays, and the gate
# keeps reporting something it can no longer see, so the log and the tree disagree
# with nothing to say which is true. When the owner re-renders, this gate turns
# red and names the line to delete. The pin is a receipt, not an excuse.
#
# TO CLEAR ONE: re-render with the command in diagrams/README.md, then DELETE the
# line. The checker refuses to pass with a pin that no longer bites, so this is
# not optional bookkeeping.
#

# 2026-09-25 against a MID-STATE: this branch had merged 5c6db3d, which edited both
# project-map .puml files without re-rendering them, and the renders on this branch
# were correspondingly behind. Main then carried diag-proto's re-renders (74e3124,
# 0512ec1), and after merging main every one of the four pins was FALSE. The gate
# said so itself, as STALE-PIN, and named the lines to delete - which is the
# anti-staleness half doing exactly its job on the author of the file, one merge
# after writing it.
#
# The lesson is kept because the failure was mine and the mechanism caught it: a
# measurement taken from a branch that is behind main describes the BRANCH, not the
# project. Measure against main before reporting a gate red, and re-measure after
# every merge - the corpus moves underneath a pin, and a pin that was true when
# written is not thereby true later.
#
# The original finding, for the record: commit 5c6db3d edited both project-map
# .puml files without re-rendering them. Main has since re-rendered both maps.
#
